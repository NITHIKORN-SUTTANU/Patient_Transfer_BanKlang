# Database foundation

Migration `014_capacity_evidence` adds immutable capacity_checks and capacity_rejections, linking considered alternatives and decision-time validation to the existing rejection event. It extends the event command-key allowlist for rejectionKind/capacityCheckId and preserves old event/booking/schedule data. Existing unclassified rejection events are not backfilled. Migration rollback is subject to the existing populated-database safeguards; do not remove operational evidence. Migrations 001–013 are unchanged.

Migration `013_dispatch_review` preserves existing verification IDs, outcomes (including unknown legacy values), notes and timestamps. It adds identity-based history pagination and same-booking correction references, rejects new unsupported outcomes/overlong notes and prevents UPDATE/DELETE through the existing append-only history guard. Legacy constraints are NOT VALID to avoid rewriting or invalidating historical records; new inserts are checked. API event IDs provide replay protection; serialized writes and expected-latest IDs prevent stale concurrent appends. Apply 013 before review APIs or daily manifest queries use these columns.

Migration `012_assignment_labels` adds immutable driver-account/name, vehicle/name/plate, verified-origin name and hospital-name snapshots to newly inserted schedules. It does not backfill historical names or alter old IDs, positions, timings or holds. Existing assignment labels remain NULL/unknown and daily exports mark any current-label fallback explicitly. Applied migrations 001–011 are unchanged. Run migration 012 before using daily exports.

The project now has a PostgreSQL 17/PostGIS development database, a versioned SQL migration runner, and synthetic fixtures. The browser prototype still uses localStorage; no existing browser data is converted, deleted, or sent to PostgreSQL.

## Local setup

1. Install/start Docker Desktop with Linux containers.
2. Copy `.env.example` to `.env` if `.env` does not already exist. Choose a local password and use the same password in the three connection settings. URL-encode special characters in connection URLs.
3. Run `npm install`.
4. Run `npm run db:start`.
5. Run `npm run db:migrate`.
6. Run `npm run db:status` to see applied migrations.
7. For fictional development records only, set `ALLOW_SYNTHETIC_SEED=true` in the local `.env`, then run `npm run db:seed`.

The initial implementation created an ignored `.env` with a randomly generated local password when no file existed. It did not replace existing settings. These credentials are local development credentials only. Never use a `VITE_` prefix for database credentials or import database scripts into browser code.

The database listens only on `127.0.0.1:54329`. Docker stores data in the `patient_transfer_database` named volume. `npm run db:stop` stops the container and preserves that volume. Do not use volume-removal commands to reset a database containing data you need.

Fixtures contain explicitly fictional users, 12 fictional village circles, locations, two vehicles, one driver, and a synthetic consent record. The circles deliberately overlap and do not represent municipal boundaries. No usable login passwords, real LINE subjects, patient bookings, or operational shift calendar are seeded. Fixture timestamps are illustrative, not production schedules.

## Migration behavior and rollback

`database/migrations/001_foundation.up.sql` creates the isolated `patient_transfer` schema and requires privileges to install `postgis` and `btree_gist`. It does not modify other application schemas. The runner keeps a checksum ledger in `public.patient_transfer_migrations` and takes an advisory lock so concurrent migration processes serialize.

Each migration and its ledger write run in one transaction. A failure rolls both back. Re-running an applied migration is a no-op; editing either applied SQL file produces a checksum error. Add a new numbered migration after application instead of editing an applied file.

Migration 004 adds controlled assistance sets to bookings and profiles, profile landmark, and nullable booking relationship (`self`/`other`). Historical relationships remain unknown; new API intake requires an explicit choice. Existing booking snapshots and legacy assistance text are preserved. Fresh installs and upgrades must run all migrations before using the updated citizen APIs. Migration/upgrade tests use temporary databases; they do not apply changes to the working development database.

Migration 005 adds deterministic consent-decision ordering so later refusal invalidates an older acceptance for future intake/profile writes, including decisions sharing a timestamp. It backfills only ordering metadata without changing recorded decisions/timestamps; historical timestamp ties conservatively put refusal last. The append-only trigger is disabled only for this metadata backfill under the migration's exclusive table lock and restored within the same transaction. Existing submitted consent snapshots remain intact. New consent writes use a database sequence; the latest decision for the current notice must be accepted.

Migration 006 adds `users.revision` with a trigger advancing it on every update, plus optional `audit_logs.before_data`/`after_data` for explicit staff-account snapshots. It preserves existing identities, password hashes and audit rows. API writes allowlist staff metadata and never store password/hash/token/LINE fields in these snapshots. Existing database access-change/session-revocation and resource-deactivation triggers remain authoritative. Account APIs additionally preserve a last active administrator and block linked-driver role changes or suspension during unfinished work.

Migration 007 preserves existing resource positions, capabilities, initial availability and windows while adding resource/window revisions, vehicle type, driver phone and nullable `retired_at`. New text metadata defaults to unknown/empty rather than fabricated values. Window changes advance the parent resource revision; updates/deletes cannot uncover unfinished committed assignments. A second schedule trigger checks active windows after the existing resource-locking guard, so retired rows cannot authorize new commitments. Metadata guards block critical resource changes during unfinished work and identity/base-position resets during holds. Driver roster linking/status changes revoke affected account sessions. API retirement retains window rows/history; existing resource holds and position-update records are never cleared by these operations. Migration apply/empty rollback/upgrade-preservation and guard cases are exercised on temporary databases.

`npm run db:rollback` rolls back the latest migration only when every application table is empty. It takes exclusive table locks before checking. A populated database, including one with synthetic seed records, is intentionally refused. For a populated deployment, use a tested backup/restore or a separately reviewed forward migration. There is no force-delete option.

The down migration drops the empty application schema. It retains extensions because other schemas may depend on them. No command automatically contracts the prototype or migrates localStorage data.

## Synthetic recovery rehearsal

Run `npm.cmd run test:recovery` with Docker Desktop running, the existing database container healthy, and local `DATABASE_TEST_ADMIN_URL` configured for port 54329. It requires the container's PostgreSQL tools and socket authentication for the configured test administrator. The command refuses remote hosts, other ports and database names outside its generated `pt_test_…` namespace. It does not read, dump, reset or restore the development application database, edit configuration or send real messages.

The drill creates a fully migrated synthetic source database, submits and assigns a booking through the real API, and records a transient notification failure. A repeatable-read exported snapshot binds both the whole-database custom-format `pg_dump` and SHA-256 comparisons of every application table plus the migration ledger. The drill runs two variants: the original in-memory plain archive and an encrypted retained archive with a separately persisted trust anchor (64 MiB stored-archive limit). Both use the same snapshot/fingerprint and service-verification path. The encrypted variant stages/publishes ciphertext, explicitly publishes its inventory anchor into a separate temporary trust store, and holds only the expected head receipt and synthetic key for recovery. It reads no plaintext recovery archive until after the source database is confirmed absent. After that loss it reloads the persisted anchor against the known receipt, rejects missing trust and a wrong key, and authenticates/decrypts the retained archive through readAnchoredBackup before restore. Keys remain injected in memory; this does not prove recovery of production key custody or a full process/host restart. After a deliberately committed post-snapshot booking, the drill declares failure and removes only its generated source database. It rejects a corrupt archive, restores the valid archive with `pg_restore --exit-on-error --single-transaction` into a newly generated database, and compares all table counts/digests before further writes.

Recovery verification checks checksummed migration history, missing post-snapshot work, surviving booking/schedule snapshots, unauthenticated/revoked/foreign-owner/admin denials, staff password login, independent role boundaries, immutable event/attempt history, pending notification processing and a consumed retry resuming with the same identity/budget. A second worker invocation does not resend accepted rows. Only injected synthetic senders are used. Fresh driver Start Trip and citizen intake through the restored API also exercise restored sequences and write constraints. All generated databases and task-owned temporary archive/trust directories are cleaned up, including on assertion failure; the existing development volume is preserved.

The six checks (target guards, both basic disaster variants, two encrypted post-snapshot acceptance variants and the opt-in quarantine variant) print only aggregate timings/counts, protection variant and recovery timestamps: dump time, restore time, total verified recovery time measured from declared source loss, and recovery-point age measured using database wall time at snapshot/failure. It checks local recovery-point age ≤1 hour and verified recovery ≤4 hours. Synthetic business time is separate from these real elapsed measurements. The small local dataset, synthetic in-memory key custody and same-container restore do not establish production RPO/RTO, protected hourly automation, approved encryption/access controls, off-host storage, retention, or hosting feasibility. Those remain SRS 3.3 / O-04 / O-07 acceptance work. No 50-user performance or monthly availability claim follows from this rehearsal.

For an actual recovery, keep notification delivery disabled until the service owner reconciles provider outcomes against the restored recovery point. Sends accepted after the snapshot may be absent from restored history. The two additional encrypted disaster cases model this with a separate temporary file-backed synthetic provider ledger that survives source loss. The injected existing LINE push adapter receives simulated HTTP 200 first acceptance and HTTP 409 with an accepted-request header on repeat requests within the modeled 24-hour key window. Fresh adapters reload the ledger; only retry identities, payload hashes, timestamps and acceptance flags are retained, without recipient subjects or message text. These are synthetic provider semantics, not live LINE validation.

Within that window, restored worker requests retain their retry keys and exact payloads, are deduplicated by the modeled provider and commit SENT without another provider acceptance. A second restored worker invocation does not resend. At expiry, a restored known retry stops as RETRY_KEY_EXPIRED and a synthetic legacy row with unknown first-attempt history stops as RETRY_HISTORY_UNKNOWN; neither calls the provider. However, rows restored with zero attempts have no surviving first-send timestamp: the worker can treat them as new sends even though the provider accepted them after the snapshot. Once provider deduplication expires, this test deliberately reproduces additional acceptances. The passing test characterizes a recovery limitation, not a safe release result. Do not infer that current retry guards make all restored pending work safe or reset budgets/keys to force delivery. Keep delivery disabled pending owner reconciliation; a protected restore quarantine/release procedure remains required before operational recovery sign-off. Establish an approved restricted backup location outside the database failure domain, encryption/key ownership, hourly scheduling with stale/failure alerts, retention/legal-hold decisions and a deployment-host recovery runbook before live acceptance. Do not use this synthetic test command as a production restore procedure.

### Opt-in synthetic restore quarantine

`scripts/database/synthetic-restore-quarantine.mjs` builds a rehearsal-only `beforeAttempt` callback for the existing notification worker. It accepts only generated local test database targets and requires an explicit restore UUID, backup trust-head hash, independent evidence path and separately pinned evidence digest. The production runner does not install it; it is not a production quarantine or release policy. Keep `ALLOW_LINE_DELIVERY=false` pending approved operational recovery procedures.

A synthetic reviewer explicitly supplies a versioned evidence file outside the restored database. It binds the restore ID, restored database hash, recovery-anchor hash, canonical review timestamp and one decision per notification state digest. Allowed decisions are HOLD, CONFIRMED_NOT_ACCEPTED and RETRY_WITHIN_WINDOW with confirmed first-provider-use time and a hashed evidence reference. The rehearsal assembles those attestations from the independent synthetic provider ledger. The gate validates their shape, pinned integrity and context; it does not independently authenticate a real reviewer or verify real provider outcomes. Key custody, authority and truth of those attestations remain external trust requirements.

The worker invokes the optional callback inside its transaction, after locking the selected notification and before any in-flight recovery, attempt reservation or provider contact. Missing/unreadable/changed evidence, wrong restore/database/anchor, future review, stale row state, duplicate/conflicting decisions, HOLD, absent decisions and expired retry-window evidence stop with RESTORE_QUARANTINE_BLOCKED. The gate changes no attempts, retry identities, status, history or operational records. All existing normal-worker guards still apply after approval. Evidence is re-read for each selected row; a new or changed notification requires new independently pinned evidence. This is per-row permission, not an atomic whole-batch send: earlier independently allowed rows can already have committed before a later blocked row stops a batch.

The real encrypted recovery case exercises eleven invalid-evidence variants with unchanged full database fingerprints and provider ledger, then permits four deduplicated synthetic retry requests with zero additional provider acceptances. Driver Start Trip and citizen intake still succeed; their newly created notifications remain blocked under the older evidence with budgets unchanged. The unguarded expired-window characterization remains in the suite to keep the original safety gap visible. Protected evidence publication, production reviewer authentication, restore-marker enforcement and mandatory production runner integration require O-07 owner decisions; direct worker calls without the optional callback remain unquarantined. No reset, automatic reconciliation, resend policy or real delivery is enabled.

## Scheduled-backup freshness rehearsal

Run `npm.cmd run test:backup` with the same local test-database/Docker prerequisites as the recovery rehearsal. It includes twenty-four controlled scheduling/storage/encryption/trust checks and two real API/PostgreSQL retained-backup restore checks (plain and encrypted). `scripts/database/backup-readiness.mjs` permits only generated local `pt_test_…` databases on port 54329, checks the connected pool's actual database before dumping, and stores no connection URL/password in metadata. Invalid private source configuration and provider errors are sanitized. The development application database is never dumped or reset.

Explicit initialization creates a new temporary store bound to its generated source and an hourly UTC schedule anchor. `runScheduledBackup` performs one supplied-clock tick, not a daemon: it selects the current hourly slot and never fabricates archives for missed earlier slots. Completed/failed slots are idempotent; a failed capture remains recorded until a later scheduled slot succeeds. There is no automatic same-slot retry, production scheduler or archive deletion. A tick whose actual start has moved into a different slot, backward clocks, future recovery points and mixed clock sources fail closed. Hourly slots are a rehearsal of the adopted baseline; real scheduling needs sufficient duration/retry headroom to keep recovery-point age continuously within one hour, subject to O-07 review.

The PostgreSQL adapter takes a conservative database wall timestamp before acquiring an exported repeatable-read snapshot, then uses the existing guarded `pg_dump` tool. Recovery-point age is measured from that timestamp, not backup completion. The job clones captured bytes, writes/syncs an archive and allowlisted checksum/timestamp manifest in a unique staging directory, verifies the stored bytes, then atomically publishes the complete directory. Partial/unpublished artifacts are reported and never promoted automatically. An interrupted response after publication is reconciled by slot lookup without another capture. Repeat calls and `readVerifiedBackup` recheck bytes/size/SHA-256; missing/corrupt archives never qualify as a verified recovery point.

`backupReadiness` returns sanitized stable finding IDs/codes for absent/stale points, missed current slots, failed latest runs, corrupt/missing archives, unpublished staging, clock conflicts and inaccessible/invalid storage. Historical missed slots and failed-run counts remain visible after a new good point restores current freshness. Age exactly one hour is within the adopted RPO bound; a pending/missed due run is reported separately, and age beyond one hour is stale. Polls and successful process exit alone do not establish a usable recovery point. Locks fail closed without automatic stealing. Store/metadata corruption never resets history.

The real test creates a synthetic citizen booking and dispatcher approval through HTTP, retains its PostgreSQL archive, commits another booking afterwards, restores the verified stored bytes into another temporary database, compares all 30 application/ledger table fingerprints and proves the later booking is absent. Notifications remain PENDING with zero attempts. Generated databases and the checked task-owned temporary directory are cleaned up. The earlier complete application/outbox recovery drill remains a separate `test:recovery` command; neither command sends real messages.

Protection defaults to `unencrypted-synthetic-rehearsal`. Passing an injected 32-byte Buffer as `encryptionKey` at initialization opts into `encrypted-synthetic-rehearsal`; the same key is required for scheduled writes, verified reads and readiness checks. The provisional rehearsal format uses Node AES-256-GCM with a fresh 12-byte random nonce, a 16-byte authentication tag and authenticated source-hash/slot/recovery-point context. Only ciphertext is persisted; decryption completes authentication before returning archive bytes to the restore caller. Wrong keys, tampering and policy mismatches fail closed; an existing successful archive is authenticated before another capture to prevent accidental key drift. Keys remain caller-owned in memory and are never included in metadata or diagnostics. No environment key, key identifier, key rotation, production provider or scheduler is selected. The plain and encrypted real-PostgreSQL test variants restore retained archives and compare application tables. Controlled tests also recompute public checksums after ciphertext tampering to prove those checksums cannot bypass archive authentication. Public inventory/manifest checksums remain untrusted against wholesale replacement, deletion or policy downgrade; deployment needs a trusted inventory/anchor and approved key/storage ownership. This local store is unsuitable for real-patient backups and does not establish approved encryption, off-host failure-domain isolation, restricted deployment ACLs, trusted inventory signing, retention/legal hold, continuous hourly execution, reviewed alert ownership/delivery or production RPO/RTO. Each archive is capped at 64 MiB and the schedule at 10,000 slots for rehearsal; these are not retention decisions. No existing configuration, applied migration or development volume changes. O-04/O-07 production storage/encryption/key ownership and scheduling decisions remain required before live acceptance.

### Independently anchored synthetic inventory

After an explicitly trusted encrypted capture, call `createBackupAnchor({ directory, source, encryptionKey })` and retain its returned version/scope/source-hash/inventory digest independently of the backup store. Creation authenticates every successful archive, includes metadata and every ordered run manifest (including failed runs) in the digest, and refuses unencrypted, empty or staged/incomplete stores. This is an explicit trust decision: creating a new anchor from an untrusted replacement store would bless that replacement. The anchor may be held in caller memory or explicitly published to the separate synthetic trust store below. Neither establishes a trusted production repository.

Use `readAnchoredBackup({ directory, source, encryptionKey, trustedAnchor, slot })` for restore bytes and `anchoredBackupReadiness({ directory, source, encryptionKey, trustedAnchor, at })` for freshness. Both require the independently supplied anchor; missing anchors fail closed. Inventory verification, archive authentication and the selected read/freshness calculation share the existing store lock. Trust failures expose a fixed sanitized code and no restore bytes; freshness remains a separate requirement even when inventory matches. The original unanchored APIs remain available for earlier rehearsals and do not claim inventory trust.

The anchor binds the exact inventory, so any new run also requires explicit advancement of the separately retained anchor. Tests prove valid encrypted archive replacement, manifest alteration with recomputed checksums, missing archives/manifests, rollback to a previously valid whole inventory and encryption-policy downgrade cannot satisfy the latest trusted anchor. An older recovery point can still be selected from a matching current inventory. The encrypted real PostgreSQL restore uses this anchored path. The persisted synthetic trust store below rehearses explicit compare-and-swap publication and interruption handling. Automatic anchor repair, production signing/key custody, off-host trust publication, retention and deployment-host adversarial filesystem protection remain unimplemented. Loss or malicious rollback of trust storage still requires independently protected custody under O-07.

### Persisted synthetic trust-anchor advancement

`scripts/database/trust-anchor-store.mjs` explicitly initializes a new trust directory separate from (and neither inside nor containing) the backup directory, resolving filesystem paths before writes. Existing directories are never reset. `advanceTrustAnchor({ directory, backupDirectory, expectedHead, nextAnchor, operationId })` requires a caller-known head receipt, or explicit null for first publication, and a stable UUID operation identity. Receipts contain revision, record hash and inventory anchor. Updates validate the complete ordered hash-linked history under an exclusive cooperating-writer lock, reject stale heads, cross-source changes and reuse of historical inventory digests, then write/sync a new revision in staging before publishing it by rename. No prior revision is rewritten.

`readTrustHead({ directory, backupDirectory, expectedHead? })` reloads the persisted head; supply a separately known expected head to detect rollback against that knowledge. Its anchor can be passed to `readAnchoredBackup` or `anchoredBackupReadiness`. Omitting the expected head explicitly trusts the persisted store as the authority: an attacker able to roll back or replace that whole store can defeat an unpinned reader. Local hash chains are integrity checks, not signatures, protected remote storage or WORM guarantees. Publishing a newly created anchor is a caller trust decision, not proof that the current backup inventory was authorized.

A lost response after publication can be reconciled by retrying the exact operation ID, prior expected head and next anchor; it returns the existing current revision without republishing. Conflicting operation reuse and a replay superseded by a later head are rejected. An interruption before publication leaves staging evidence and blocks reads/updates for review; corrupt/missing records and stale locks also fail closed. There is no automatic lock stealing, staging promotion, deletion, repair or reset. Injected fault tests exercise before/after publication and concurrent writers; the real encrypted PostgreSQL test publishes and reloads the separate trust anchor before restoring.

Files are synced and publication is atomic for the tested cooperating processes. OS crash/power-loss directory durability, process-kill recovery, separate-device failure domains, Windows deployment ACLs and production retention/key custody are unverified. A pinned receipt detects known rollback; it cannot recover a lost trusted receipt/store. Each record is limited to 4 KiB and history to 10,000 revisions for the rehearsal. These are test limits, not approved production retention. No scheduler, automatic cleanup or delivery is enabled.

## Tables and responsibilities

- Identity: `users`, `auth_sessions`, `consent_records`.
- Geography/master data: `locations`, `service_villages`, `hospitals`, `service_settings`, `service_closures`.
- Profiles/resources: `patient_profiles`, `vehicles`, `drivers`, `availability_windows`.
- Operations: `bookings`, `schedules`, `resource_holds`, `trip_events`, `trip_incidents`, `trip_dispositions`, `verification_logs`.
- Delivery/accountability: `notifications`, `audit_logs`.

Times use `timestamptz`; closure dates use Bangkok calendar dates. Locations use `geography` with SRID 4326. Villages support either an approved polygon or an approved center/radius. The API must select and validate the authorized service area with `ST_Covers` or `ST_DWithin` as appropriate.

The database enforces 48-hour submission notice, accepted consent belonging to the requester, profile ownership, route-time arithmetic, the fixed 20/30-minute rules, full 06:00–16:00 operating windows, and independent vehicle/driver overlap exclusions for committed unreleased reservations. Proposals do not reserve resources. Adjacent half-open intervals are allowed.

Commit guards reject closures, operational holds, inactive/ineligible resources, and missing availability windows. Resource deactivation is blocked when unfinished assignments exist. A new closure flags affected assignments for dispatcher review without cancelling them. User suspension, role change, or password change increments the access version and revokes existing sessions. The API now checks these sessions and versions; see `API.md`.

Events, audit entries, consent records, and final patient dispositions reject row updates/deletes. Append corrections rather than overwriting history. Retention/deletion requires an approved maintenance process; this foundation does not implement it. ABORTED requires a start timestamp and patient disposition by transaction commit.

## API and remaining release integration

The authenticated API foundation is implemented in `server/`, including role/ownership checks, optimistic revisions, transactional writes, and serialized calendar/readiness updates. The schema is not an authorization boundary by itself. A restricted production runtime database role and deployment policy remain to be installed. Do not expose the database directly to citizens or use the local migration owner as the production public API identity.

The server contract (implemented for the foundation endpoints; external identity/privacy/release integrations remain pending):

1. Derive actor identity and role from validated authentication. Map the driver account to `drivers.id`; it is distinct from `users.id`.
2. Validate LINE identity, privacy notice version, caregiver authority, supported hospital/service area, transport-only notes, route provenance, and lifecycle commands.
3. Start a database transaction and lock the booking and relevant resources consistently. Rerun domain scheduling checks using the latest committed data, including previous-hospital continuity, actual delays, readiness, and affected later trips.
4. Apply optimistic revision checks, preserve old schedule snapshots, and commit the lifecycle event, booking update, both reservations, audit entry, and notification outbox row together. A deferred patient disposition check permits ABORTED and its disposition to be written in that same transaction.
5. Check the user's active state, access version, and session revocation on authenticated requests. Never treat the presence of a session row as sufficient authentication.
6. Require dispatcher authority before ending incidents or releasing holds. Schedule release alone does not confirm operational readiness. Holds must remain after failed pickup or ABORTED until readiness is verified.
7. Serialize resource-hold/readiness changes with the same vehicle/driver row locks used by schedule commits. Handle exclusion violations, revision conflicts, and deadlocks without partial assignment or duplicate notifications.

Database constraints do not replace domain validation. In particular, location continuity, correct state transitions, downstream route recalculation, role enforcement, and late-trip readiness require the server. Closure changes racing with assignment must also serialize in the API transaction. Do not silently overwrite or cancel existing trips.

Migrations 002 and 003 add explicit pickup waiting, handoff/position records, modification commands, execution versions, an immutable citizen cancellation cutoff, ordered event sequences, and unique open resource holds. Existing schedules receive zero waiting. Applied migration 001 is preserved unchanged.

## Verification
