# Authenticated API Foundation

## Booking-list pagination

`GET /api/bookings` and driver-only `GET /api/driver/history` return `{ bookings, nextCursor }`. Pages contain at most 100 rows; a null cursor means no more rows in that read. Pass the opaque cursor as `?cursor=<URL-encoded value>`. Operational order is appointment ascending then booking UUID ascending; minimized driver history uses both descending. The timestamp boundary preserves PostgreSQL microseconds, including when many appointments tie. Malformed or differently scoped cursors are rejected; a cursor is a position, never an access grant.

Authentication and role/owner/driver/current-shift or active-overrun checks apply on every page. History still contains only ID/reference/status/appointment and uses the latest committed assigned driver. Ended operational details remain inaccessible to drivers. Each page selects and hydrates within one read-only repeatable-read database transaction. Pages across separate requests are not one frozen snapshot: new or moved appointments before an existing boundary require refresh; command revisions and execution versions remain authoritative.

The original dispatcher and driver screens offer small Thai load-more controls. Dispatcher counts, local search/date/status filters and predecessor choices cover the loaded range, with an explicit partial-range notice while more data exists. Refresh rebuilds the already requested range from page one and deduplicates IDs, so ended/reassigned rows do not persist from old pages. Failed range reads clear operational data and show an error; refreshing retries the range. Direct dispatcher booking links continue to fetch an authorized focused booking beyond loaded pages. The existing citizen own-booking list also offers a Thai load-more control and loaded-record count while more pages exist. Its range is bound to the authenticated owner and kept in memory. Refresh and returning from details rebuild the requested range; a document reload starts again at page one. An independently fetched focused booking is removed from list counts when returning to the list unless it belongs to the loaded range. Transport/read failure clears operational rows, keeps the existing retry control, and never shows a successful empty list. Status/cancellation entries always re-fetch the authoritative own detail, including records beyond the first page; stale cancellation commands remain subject to server revision and Start Trip/reassignment locks.

Operational pages hydrate the selected IDs in one parameterized bulk query within that same snapshot, then restore the selected cursor order and authorize/serialize every row. The shared single-booking query still serves direct detail and locked command reads. This removes up to 100 independent hydration round trips per page without caching across requests or weakening ownership checks. Driver history retains its separate minimal projection and does not hydrate patient details.

## Capacity rejection evidence (FR-028)

Dispatcher-only `POST /api/bookings/:id/capacity-checks` accepts `{ expectedRevision, alternatives, explanation }`. Work must be current, unstarted REQUESTED/APPROVED/SCHEDULED with no unresolved configuration review. Provide 1–30 alternatives; each uses the existing scheduling-selection fields: vehicleId, driverId, originLocationId, optional originKind/previousBookingId/arrangement/pickupWaitingMinutes. Estimates, availability flags and conflict conclusions cannot be supplied by the client. Explanation is required, trimmed and at most 1000 Unicode code points. The existing rejection dialog collects multiple vehicle/driver/origin choices, optional predecessor reference and the explanation without replacing the screen.

The server obtains real configured routes and uses the existing authoritative scheduling validator against committed reservations, effective continuations, shifts, capabilities, positions, holds, service hours, closures and downstream chains. It records each selected alternative's routes/provenance and available/unavailable/not_capacity result, actor/time and explanation in immutable capacity_checks with a minimized audit. Checks never reserve resources or change booking state. A viable alternative prevents capacity rejection. Hours/lead-time/invalid-input/configuration issues are not evidence of capacity shortage. Provider failures or an already-invalid committed timeline stop investigation rather than fabricating unavailability. Only selected alternatives are investigated: this is human investigation evidence, not an exhaustive automatic planner or proof that all possible arrangements were searched. Dispatchers remain responsible for truthful category/alternative selection and reasons.

New REJECT commands require `rejectionKind: "capacity" | "other"` alongside the existing nonblank public reason. Capacity rejection additionally requires capacityCheckId from the same dispatcher and booking, marked rejectable. Other reasons must not attach a capacity check. Exact replay of an already-recorded legacy rejection remains supported without rewriting its old command. Missing categories on new decisions are rejected.

At confirmation, the server compares booking/resource/window/account/master/closure/position/hold/reservation state against the captured fingerprint; any relevant change (conservatively including unrelated changes in these state sets) requires investigation again. It then re-routes and revalidates every considered alternative in the same serialized transaction. No arbitrary fixed freshness TTL is substituted for this decision-time check. A fresh immutable check is linked to the original check and rejection event in capacity_rejections. Fresh evidence, lifecycle, linkage, audit and outbox commit/roll back together; retries do not repeat the decision. The dispatcher review endpoint displays the linked decision evidence. Citizen/driver/admin responses do not expose these operational records or explanations; citizens retain their authorized public rejection reason.

Migration 014 adds append-only evidence/link tables and extends the event-key allowlist without changing old events. Applied migrations 001–013 remain unchanged. Records remain subject to municipal retention approval. Routing-dependent performance and exhaustive municipal arrangement review are separate acceptance evidence.

## Dispatcher review evidence (SRS 2.3.1 / FR-030)

`GET /api/bookings/:id/review` is dispatcher-only. It returns `bookingId`, `latestId`, `duplicates`, the newest 50 verification entries and `nextCursor`; pass `?cursor=<entry UUID>` for earlier records. A cursor must belong to the same booking. Review reads run under the operational transaction lock so the history/latest identity and warning comparison form one consistent result. No citizen/admin/driver duplicate lookup is exposed, and other requesters' patient/contact details are not returned in warnings. Warnings contain reference, ID, current status and matching criteria, linking to the existing authenticated dispatcher detail screen.

Matching is deliberately exact: names use Unicode NFC, trimmed/collapsed whitespace and lowercase; phone comparison removes whitespace/hyphens and converts +66 to local 0. A warning requires matching normalized name, contact, hospital and appointment instant, or the same saved-profile ID and appointment instant even when contact differs. Matching names alone do not warn. All booking states can be reviewed; warnings never establish identity or automatically merge, reject or cancel work. No fuzzy similarity policy is added.

`POST /api/bookings/:id/verification` accepts exactly `eventId` (UUID), `expectedLatestId` (UUID or null), `outcome`, `notes` and optional `correctsId` (UUID or null). Outcomes are `confirmed`, `correction_needed`, `unreachable` or `requester_declined`. Notes are trimmed, at most 1000 Unicode code points, and restricted by operator instructions to permitted transport/call information; no automated clinical-text classifier is claimed. Actor and time come from the authenticated session/server. A correction appends a new entry referencing the current latest record and requires an explanation; old rows remain immutable. Stale latest IDs, conflicting event reuse and cross-booking corrections fail closed. Exact replay returns the existing record without duplicate audit/history writes.

Verification and minimized audit commit together; late audit failure rolls back the entry. Writes do not change lifecycle/revisions, reservations, holds or notification/outbox state. The original dispatcher detail dialog has explicit load, outcome, notes, correction and paginated history controls. Failed writes preserve input; pending saves block dismissal/decision/navigation through the panel. Loading older pages does not silently advance the user's latest-entry precondition. Daily manifests retain all permitted verification history and label correction references. Admin audit responses exclude verification notes and booking references.

Migration 013 adds cursor identity, same-booking correction links, append-only protection and new-write outcome/note checks. Existing legacy values/timestamps are preserved without inventing structured outcomes or correction links; cursor revisions do not assert historical recording times. Existing migrations 001–012 are unchanged. FR-028 capacity/conflict evidence is implemented by the capacity investigation and rejection contract above.

## Monthly aggregate workbook (FR-047)

`POST /api/reports/monthly` accepts exactly `{ "month": "YYYY-MM" }` and returns an `.xlsx` attachment, report ID and no-store headers. Active dispatcher and admin sessions are allowed; citizen, driver and anonymous requests are denied. The original dispatcher tracking and admin history pages provide small collapsed download controls. The date input is retained after failure, and success is shown only after an audited attachment response. Daily patient-bearing exports remain dispatcher-only.

The workbook has exactly three sheets: service summary, totals for all 12 villages (including zero rows), and hospital/fleet summaries. Every sheet states Bangkok period [start midnight, next-month midnight), filters, report ID, as-of and generation time. One SQL statement captures all submitted bookings in the appointment month and the village catalog; it does not select patient names, contact, pickup fields, booking IDs/references or notes. Rendering occurs outside the operational lock, then current authority is rechecked and the export audit commits before bytes are returned. A failed audit yields no attachment or success audit. Separate exports are independent snapshots; there is no persistent report cache.

Each booking has exactly one outcome bucket, separating ABORTED, failed pickup and other cancellation. Approval activity counts distinct cohort bookings with an APPROVE event by as-of and is labeled separately; combined cancellation is explicitly the sum of its two subcategories and is never added again. Completion percentage is `completed / (completed + aborted + failed_pickup) × 100`, displayed to one decimal; zero denominator is `N/A`. All group totals/rates use the same cohort and definitions.

Hospital/fleet sheet sections are separate partitions by hospital, vehicle, driver, mobility and outcome: each dimension totals to the full cohort, and dimensions must not be added together. Resource attribution uses the latest committed assignment, including released history; uncommitted proposals remain unassigned. Hospital attribution uses the latest recorded destination, or booking destination if no continuation exists. Groups use stable resource IDs and retain distinct stored labels; unknown historical names are explicit. Village labels are marked current. Text remains literal Excel strings. The audit contains actor/time/month/format/cohort/attribution/interval/as-of/count, without cohort rows. No migration or new dependency is required. Municipal final field/attribution acceptance O-06 remains pending.

The API/domain/database/LINE foundation is implemented and tested. The committed UI (`bf95b2e`) is preserved. Citizen core, dispatcher, driver and admin account management use authenticated APIs. Resource/availability management is connected; hospital/village/settings administration and other SRS features remain pending. Staff login is at `/staff/login`. Follow `../plans/INTEGRATION-PLAN.md` and `../design/UI-BASELINE.md`.

The Node.js API connects domain logic to PostgreSQL/PostGIS. React screens retain their original design. Citizen LIFF verification uses the original SDK ID token and the server verifier; there is no browser identity override or fallback. See `LINE-SETUP.md` for required configuration and live LINE validation.

## Start locally

1. Follow `DATABASE.md`, start Docker, and run `npm run db:migrate`. Migrations 002–011 expand the existing schema; applied migration sources are unchanged.
2. To create a staff account, set `STAFF_USERNAME`, `STAFF_PASSWORD` (12–512 characters), `STAFF_NAME`, and `STAFF_ROLE` (`admin`, `dispatcher`, or `driver`) through local environment variables or the ignored `.env`. Run `npm run db:create-staff`. It creates a new account only; it does not replace an existing account or print the password. Remove setup variables afterward.
3. A driver account also needs an active driver roster record, verified location/readiness, and availability windows. Synthetic seed users have no usable password unless explicitly configured.
4. Run `npm run dev:api`. The server binds to `127.0.0.1:3001`; `API_PORT` can change the port. It never publishes a service by itself.
5. Log in with `POST /api/auth/login`, then send `Authorization: Bearer <token>` on authenticated requests. Tokens are not logged and only their SHA-256 hashes are stored. Staff passwords use salted scrypt.

`PRIVACY_NOTICE_VERSION` selects the current notice identifier (default `development-v1`, not an approved municipal notice). `FRONTEND_ORIGIN` optionally enables CORS for one exact UI origin. Set `OSRM_URL` to an approved routing service before real scheduling. Without routing configuration, schedule/assignment requests return 503 and retain the existing booking state.

There is no public synthetic citizen-login endpoint or password registration for citizens. `/api/auth/line` verifies the original LIFF ID token with LINE before issuing a citizen session. The user does not have channel IDs yet, so live LINE validation remains pending. Tests inject synthetic providers or seed synthetic sessions into temporary databases; neither is a runtime login bypass.

## Endpoints

All mutation bodies are JSON. Unknown intake fields, including clinical fields, are rejected. The API does not accept client-supplied actor roles, requester IDs, route durations, lifecycle timestamps, or booking status.

Resource-readiness confirmations validate the selected resource's physical location, active work and turnaround. After the last hold of an ended trip is released, its open incident is finalized with a revision update and retained incident/audit history. Partial resource confirmation leaves that incident open; active-trip incidents are not finalized through this path.

The original driver screens now use this API through verified roster identity. Driver operational lists/details exclude terminal trips; `/api/driver/history` returns only references, statuses and appointment dates. Verified origin and assigned-vehicle names accompany active jobs. Driver hold flags describe their current assigned resources, while dispatchers retain visibility of old-crew holds after reassignment.

### Staff account administration

Create body: `name`, `username`, lowercase `role` (`admin`, `dispatcher`, `driver`), boolean `active`, `password` (12–512 characters), and required `reason`. Update sends the same metadata plus current `expectedRevision`; omit `password` to retain it, or supply a new password explicitly. Unknown fields and citizen targets are rejected. Responses contain only `id`, `name`, `username`, `role`, `active`, `revision`.

All account writes use the existing serialized transaction/authentication boundary. Migration 006 adds revision advancement for every account update and allowlisted administrative before/after audit snapshots. Passwords/hashes/tokens/LINE data are excluded from audit and responses. Suspension, role changes and password resets revoke prior sessions through the existing database trigger; the next protected request fails. Stale revisions, duplicate usernames, disabling/demoting the last active administrator, changing a linked driver's role and suspending a driver with unfinished operational work are blocked. Stable error codes identify these safeguards without exposing SQL details. Creation is not idempotent: after an uncertain response, reload accounts and reconcile before retrying.

The original `/admin/*` screens require verified admin identity. Account/resource/window modals await the server, lock pending writes and retain input on failure. Hospital/village/depot/closure forms also await revisioned, audited writes. History uses aggregate counts, not patient-bearing booking records. Administrative reads never fall back to browser demo data.

### Resource and availability administration

All resource writes require `name`, boolean `active`, a nonempty set of `capabilities` (`standard`, `wheelchair`, `stretcher`) and `reason`. Vehicles additionally require `plate`, `vehicleType`; drivers require `userId`, `phone` (normalized domestic 9–10 digits). Creation additionally requires an active depot/hospital `locationId`, explicit-zone `availableAt` and `initialPositionConfirmed=true`. No working windows are invented. Updates require current `expectedRevision` and reject initial-position fields, so metadata edits cannot reset position/availability or release holds.

Critical changes (deactivation, capabilities, plate or driver-account binding) are blocked during unfinished committed work. Driver relinking also requires no unresolved holds and `sameDriverConfirmed=true`; this confirms a new login account for the same physical driver, not substitution of a different person under the old roster ID. The confirmation is audited. Roster creation, activation/deactivation or account relinking revoke affected prior sessions; activation cannot revive old tokens. Driver account activity and roster activation remain separate.

Window creation requires `expectedResourceRevision`, `startsAt`, `endsAt`, `reason`; both timestamps require explicit timezone and end must follow start. Update also requires `expectedRevision`; retirement requires both revisions and reason. Every window change advances its resource revision. A window cannot be moved to another resource. Update/retirement must leave every unfinished committed trip covered from departure through planned readiness by an active window. A required interval fails atomically with `ASSIGNMENT_WINDOW_REQUIRED`, leaving the window, resource revision and audit unchanged. Retired windows remain stored but cannot authorize planning, shift access or Start Trip. Overlapping availability windows do not reserve resources or bypass assignment exclusions. Scheduling/service hours and readiness checks remain authoritative.

Migration 007 adds resource/window revisions, vehicle type, driver phone and window retirement. Database triggers independently guard unfinished work, held identity/base-position changes, retired-window use and roster session revocation. Capabilities are serialized as JSON arrays at the PostgreSQL boundary, including the scheduling loader, to avoid custom-enum-array string results. Resources are logically removed by deactivation, not destructive deletion.

### Citizen intake

Saved-profile create/update bodies require `consentId`, `patientName`, `contactPhone`, `mobility`, `villageId`, `pickupAddress`, `latitude` and `longitude`; optional `landmark` and `assistance` default to empty values. The server derives ownership from authentication, rejects unknown fields and checks active village geometry. Updates return 404 for profiles outside the requester scope. Writes and audit entries commit together. Each update creates a new saved pickup location without changing old locations or booking snapshots. Lists contain only own currently eligible village/location records; eligibility is rechecked on every save and booking submission. Existing citizen screens offer profile selection/review and optional profile saving independently of submitted snapshots.

Required fields: `consentId`, `bookingFor` (`self` or `other`), `patientName`, `requesterName`, `contactPhone`, `pickupAddress`, `latitude`, `longitude`, `villageId`, `hospitalId`, `mobility`, `appointmentAt`. Optional: `patientProfileId`, `landmark`, `assistance`.

Intake and profiles share server validation: trim text before measuring Unicode code points (name/requester 120, address/landmark 1,000); remove phone whitespace/hyphens and normalize `+66` to domestic ten-digit format. `assistance` is a set containing only `boarding_support` and/or `caregiver_accompanies`; omission means none. Unknown codes, duplicates, nulls and non-arrays fail with a field-specific error. Mobility remains separate. Booking details expose submitted assistance/landmark to authorized citizens, dispatchers and operational drivers; requester/profile metadata is limited to the owner and dispatcher. Minimized driver history is unchanged.

Migration 004 adds controlled assistance arrays to bookings/profiles, profile landmark and booking relationship. Existing relationships stay null because they were never captured. Existing legacy `additional_assistance` text is preserved; it is not accepted as new free-text intake. Migration 005 adds ordering for consent decisions: intake/profile writes require the latest accepted decision for the current notice. Later refusal blocks reuse of older acceptance; subsequent re-acceptance can authorize new intake. Old bookings retain their original consent snapshots. A stale decision returns `details.field=consentId`, allowing the citizen UI to request a fresh decision without clearing the draft. Apply new migrations before running this API version. Notification delivery remains separately gated.

Mobility is `standard`, `wheelchair`, or `stretcher`. Appointments need an explicit timezone and at least 48 hours' notice. There is no maximum advance horizon. Intake checks notice version/ownership, accepted consent, profile ownership, service-area geometry, supported hospital, closures, and the necessary appointment-hour bounds. Full travel-dependent hours and resource checks occur during scheduling. A valid submission remains REQUESTED; it is not automatic approval.

### Lifecycle commands

```json
{
  "eventId": "client-generated-uuid",
  "expectedRevision": 4,
  "expectedExecutionVersion": 0,
  "command": { "type": "START_TRIP" }
}
```

Use a valid UUID for `eventId`. `expectedRevision` is the last read booking revision. Driver commands after reassignment must include the current execution version. Reusing the same lifecycle event ID with the same actor/command is idempotent; conflicting reuse fails. Assignment and modification endpoints reject stale revisions instead of claiming an old request changed the latest assignment.

Supported commands: `APPROVE`, `REJECT`, `START_TRIP`, `UNDO_START`, `DEPART_ORIGIN`, `CONFIRM_PICKUP`, `DEPART_FOR_HOSPITAL`, `CONFIRM_HANDOVER`, `CANCEL`, `FAILED_PICKUP`, `REPORT_INCIDENT`, `RESOLVE_INCIDENT`, `ABORT`, `CONFIRM_READY`, `CORRECT_MILESTONE`. Schedule confirmation/assignment/modification use their dedicated endpoints so they cannot bypass scheduling checks.

Reason-bearing commands require a nonempty `reason`. ABORT additionally requires `endedAt`, `location`, and `disposition`. Correction requires `target`, `reason`, and boolean `physicalStateConfirmed`. Actual pickup cannot be rolled back as a correction; use incident handling. Transport notes must exclude diagnoses and other prohibited clinical information.

Driver Start Trip is separate from departure, is limited to the planned service day and active shift, and rejects a busy/held resource. Departure cannot precede planned departure. Departure for hospital respects the explicit planned pickup waiting allowance. Driver actual handover creates a readiness hold; normal readiness cannot precede either planned readiness or actual handover plus 30 minutes.

### Scheduling and modification bodies

Required: `eventId`, `expectedRevision`, `vehicleId`, `driverId`, `originLocationId`. Optional: `originKind` (default `depot`), `previousBookingId`, `pickupWaitingMinutes` (default zero). Modification additionally requires `reason`.

Modification can include `bookingChanges` with `appointmentAt`, `hospitalId`, `latitude`, `longitude`, `pickupAddress`, or `villageId`. Changed details, fresh routes, resource revalidation, event/audit, schedule replacement, and notifications commit together. Failure rolls back the detail changes as well as the proposed assignment.

The server obtains route legs itself and verifies depot/hospital identities. Domain scheduling uses hospital location IDs internally for origin continuity; the API intake `hospitalId` identifies the hospital master record. Earlier pickup adds whole minutes of planned waiting at pickup; verified route estimates and the hospital target are unchanged.

After Start Trip, modification also requires `arrangement` containing a verified `locationId`, recent `confirmedAt` (an ISO timestamp no more than five minutes before server time, not in the future or before the current start), and transport-only `note`. Retained resources require a `handoff` origin and verified positioning. Released old resources remain held until dispatcher readiness confirmation. The replacement execution is ASSIGNED with a new Start Trip requirement; old events and the citizen cancellation cutoff remain intact. Reassignment never unlocks citizen cancellation after the trip has begun. Retaining either current resource after Start Trip requires explicit originKind=handoff; a depot/other origin returns 409 before schedule or position writes. Mismatched arrangement/origin locations remain a validation failure. Confirmed retained-resource positions append history; released resources acquire a hold only when this booking/resource does not already have an open one. An existing incident hold remains unchanged until separate readiness; reassignment does not duplicate or reset its start/reason. A retained driver still needs the new execution revision and a new Start Trip.

### Transactions and errors

All operational API writes serialize using one PostgreSQL transaction advisory lock, then use one connection for checks and writes. This deliberately favors correctness for a small fleet over maximum write throughput. Assignment updates reservations, booking revision, immutable event, audit entry, and notification outbox together. Both database exclusion constraints remain independent safeguards.

HTTP status: 400 invalid body, 401 missing/revoked session, 403 forbidden role/ownership, 404 missing record, 409 stale state/conflict, 413 body too large, 415 wrong content type, 422 rejected data/constraint, 429 login rate limit, 503 unavailable routing. Internal SQL details are not returned to clients.

Sessions are checked against current user state and access version on requests. Operational writes also lock identity/session rows during the transaction. The local login rate limit is in-process; production needs a shared/edge limiter, TLS, a restricted runtime database role, approved privacy configuration, and deployment controls. These are tracked release integrations, not completed security certification.

Intake returns the fresh booking row already hydrated for requester/dispatcher publication, after both publication writes succeed. Notification/alert insertion does not mutate booking state under the current migration baseline. This avoids a duplicate read inside the serialized intake transaction. The API still waits for transaction commit before returning HTTP 201; publication or deferred-commit failure rolls back the booking and outbox together. Direct detail reads and subsequent lifecycle/scheduling commands retain their existing authoritative hydration boundaries.

### Service geography and closure administration

Admin-only GET /api/admin/service-data returns master records, revisions and an aggregate pending-review count, excluding patient/booking identifiers. POST /api/admin/hospitals and /api/admin/villages create records; POST to the corresponding /:id updates a record with expectedRevision. Hospital fields are name, active, latitude, longitude and reason. Village fields include number (1–12), name, active, shape and reason, with either circle coordinates/radiusMetres or valid GeoJSON MultiPolygon geometry. POST /api/admin/depot requires name, coordinates, reason and the current settings revision. POST /api/admin/closures requires date/reason, with active and expectedRevision for updates; active=false reopens a date without deleting history. Fixed service hours and scheduling constants cannot be edited.

Coordinate updates insert location versions; existing bookings and schedule destination snapshots remain unchanged. Affected unstarted work is flagged for review. Dispatcher-only POST /api/bookings/:id/configuration-preview validates current geography, routes and resource rules without mutation. It takes expectedRevision and the normal resource/origin/waiting selection and returns configurationRevision plus calculated schedule. Explicit acceptance through schedule or modification requires acceptConfiguration=true, expectedConfigurationRevision and reason, and revalidates everything atomically. Scheduled proposals remain non-reserving until separate assignment. Failure preserves prior locations/schedules; started work cannot accept master-coordinate replacement. Post-pickup changes use the separate destination boundary below.

### Post-pickup destination continuation (FR-051)

Dispatcher-only POST /api/bookings/:id/destination-preview calculates a non-mutating continuation. POST /api/bookings/:id/destination commits it. Both require expectedRevision, expectedExecutionVersion, hospitalId, reason, confirmedPhase (PICKED_UP or IN_TRANSIT), confirmedAt (explicit timezone), and currentLocation { latitude, longitude, label }. Commit additionally requires a UUID eventId. Fields are allowlisted; current location is manually/physically confirmed rather than taken from the submitted pickup. Confirmation must be within five minutes, not in the future, after Start Trip and after actual pickup. The confirmed phase must equal the current active phase. Destination must be active/supported and differ from the current destination or its location version.

The server obtains a verified route, respects any remaining pickup waiting allowance, and records revised arrival, readiness and lateness separately from the original target and appointment. Readiness is the later of original planned readiness and revised arrival plus 30 minutes. Already onboard work can overrun original hours/window end; its original schedule/window proof remains intact, while effective intervals, capabilities, current holds and later resource/origin commitments are revalidated. Conflicting later work must be resolved explicitly before continuation. Preview returns version, hospitalId/name/locationId, arrivalAt, readyAt, latenessSeconds, appointmentLatenessSeconds and recordedAt. Commit returns the scoped booking with current destination, destinationRevision and effective schedule arrival/readiness; original departure/pickup and appointment remain unchanged. Dispatcher responses additionally expose destinationHistory (version/name/estimates/reason/time/route provenance); driver/owner responses omit that operational history.

Commit atomically appends an immutable trip_route_legs version linked to its predecessor and lifecycle event, advances booking and execution revisions, audits the reason and queues requester/current-driver outbox entries. It retains booking/reference, phase, actual pickup, assigned resources, incident flags and holds. Driver commands with old revisions fail. Identical eventId/request/actor replay is idempotent; identifier reuse with different data fails. Route or storage failure rolls back booking/events/audit/outbox/route legs together. This endpoint does not resolve incidents, reassign an onboard patient, restart pickup or reopen cancellation. ABORT remains a separate real end-without-handover operation; released schedules do not hide recorded destination revisions.

Run npm run test:destination:integration for the original dispatcher and refreshed driver screen journey plus real API/PostgreSQL checks with synthetic routing. It covers permissions, stale revisions/confirmations, preserved commitments, duplicate replay, two route versions, holds, late continuation, ABORT, downstream conflicts, raw database conflict protection and an injected late write failure. It does not establish live routing/LINE delivery or full municipal acceptance.

### Notification retry and failure review

The separately gated worker permits five attempts total, using delays of 1, 5, 30 and 120 minutes from the preceding failure completion. A valid later Retry-After (seconds or HTTP date) takes precedence. Only network/rate-limit/server failures are retryable; inactive/unverified recipients and permanent provider errors stop immediately. Provider text, tokens and LINE subjects are not stored in diagnostic codes or returned by review APIs. LINE acceptance is not delivery/read confirmation. A retry conflict is accepted only with the provider's accepted-request header.

Before external I/O, the worker durably reserves the attempt budget and retains a session advisory lock through completion. A lost process/unknown outcome is reconciled on a later worker invocation after a 30-second recovery boundary, without restoring its consumed attempt. This records LINE_DELIVERY_UNCERTAIN and schedules the next permitted retry or stops after attempt five. The notification UUID remains the same provider retry key. Legacy retry rows without a known first attempt stop as RETRY_HISTORY_UNKNOWN. Keys at or beyond the provider's 24-hour window stop as RETRY_KEY_EXPIRED, including when a long Retry-After would cross that boundary; staff must reconcile instead of sending a potentially duplicate request. No automatic resend/reset is exposed by review controls.

Dispatcher GET /api/notification-failures lists failed deliveries with attempt count, sanitized failure, next retry or terminal state, booking/event/recipient references and named review metadata. Admin GET /api/admin/notification-failures exposes only sanitized configuration/uncertain-delivery diagnostics, separate technical review metadata and configuration-presence/delivery-enabled booleans; it excludes booking/event/recipient identifiers, patient details, credentials and LINE subjects. Both return failures, total, pending and nextCursor; use ?cursor=notificationUuid for older records (50 per page).

POST /api/notification-failures/:id or the admin equivalent accepts action=claim and expectedRevision. It claims the current user's own review lane; another active reviewer cannot be displaced, while an inactive or role-reduced owner can be replaced. Action=review additionally requires note, a nonempty result/next action up to 1000 characters, and the current claimant's identity. Only terminal failures can be claimed/reviewed. Stale edits fail and retain browser input; reviewed results remain visible without changing FAILED to SENT, resetting attempts, resending or mutating a booking. Dispatcher and technical reviews are independent and audited. Duty assignment during service hours and the municipality's named technical service owner remain operational responsibilities; the authenticated admin diagnostic panel is the technical alert surface, not an external email/LINE alert.

The LINE retry-key behavior is described in [LINE's retry guide](https://developers.line.biz/en/docs/messaging-api/retrying-api-request/).

### Event-specific notification messages and dispatcher work alerts

New notification rows snapshot a versioned, allowlisted event payload inside the booking transaction. Request receipt goes to the requester; final assignment, schedule/assignment changes, destination revision, cancellation/rejection where applicable, incidents/resolution, completion and ABORT go to the requester and intended current/affected driver. Failed pickup sends the requester its distinct cancellation/readiness outcome; the reporting driver receives the committed command response. Ordinary reporting-driver milestones do not add redundant LINE acknowledgement messages. Dispatchers receive authenticated web alerts rather than synthetic/unverified staff LINE recipients.

Reassignment gives the owner a change notice, the old driver an explicit REMOVED notice without pickup timing or old-job detail link, and the new driver an ASSIGNED notice with confirmed pickup timing. An unchanged driver receives one changed-assignment notice. Roster IDs resolve to verified account IDs before canonical event/recipient deduplication; the owner view takes precedence if one account is reached through multiple audiences. Request receipts use a separate identity namespace so choosing the booking UUID as a later event UUID cannot suppress that event.

Message bodies contain reference, event/status meaning, necessary timing and event timestamp plus a current authenticated link. Proposed-schedule pickup is explicitly provisional; original appointments are not rewritten. Completion timing retains at least actual handover plus 30 minutes and states that readiness still needs separate confirmation. ABORTED never says completed. Patient/requester names, contact, pickup coordinates/address, reasons and detailed dispositions are excluded. Rejection/cancellation reasons remain behind authorized details links.

PUBLIC_APP_URL must be an approved HTTPS origin without credentials/path/query/fragment. Citizen links enter the existing /booking/status/:id surface and LIFF verification; driver links enter staff login with a whitelisted internal next path. Terminal drivers go to minimized history; removed drivers go to their current job list. Authorization is rechecked by existing API boundaries, so old links do not restore ownership/assignment or suspended access. Dispatcher deep links fetch their booking explicitly when it falls outside the first 100 list rows. The final body and recipient LINE subject freeze before the first send and remain unchanged under the same retry key. Missing/invalid origin, changed recipient binding/access, absent historical event payload or unknown prior retry payload stops for visible reconciliation. Historical snapshots are not invented on migration.

Dispatcher-only GET /api/dispatcher-alerts returns alerts, unread and nextCursor (50 per page; optional cursor UUID). Events include reference, event/status description, necessary timing, timestamp and internal authorized link. POST /api/dispatcher-alerts/:id/acknowledgement accepts an empty JSON object and records the authenticated dispatcher's acknowledgement once. Acknowledgement is per dispatcher, append-only and audited; it is not a LINE read receipt and never changes a booking, delivery status or retry budget. Alert, recipient outbox, lifecycle and audit writes commit/roll back together.

Repeat npm run test:messages and npm run test:messages:integration. # Daily dispatch manifest (FR-047)

`POST /api/reports/daily` accepts exactly `{ "date": "YYYY-MM-DD", "format": "xlsx" | "pdf" }`. Only an active authenticated dispatcher may download these patient-bearing files; admin, citizen and driver roles are denied. The original tracking page contains the export controls. Responses are attachments with the appropriate MIME type, `Content-Disposition`, `X-Report-Id` and no-store headers. Invalid dates, formats and unknown input fields fail before generation.

The cohort uses appointment time in Asia/Bangkok, from selected midnight inclusive to the next midnight exclusive, and includes only bookings with committed assignment history, including released/cancelled/aborted/completed work. Pending requests and uncommitted proposals are excluded. Each request captures one consistent SQL dataset and renders from it outside the operational lock; separate downloads have independent as-of snapshots and can differ after operational changes. Current authority is checked again before the export audit commits and the attachment is returned. Audit records contain actor, time, format, date, interval, cohort, as-of and row count, without patient rows.

Fields cover section 2.7, historical crew/origin references, continuation history and permitted verification/exception notes. Clinical fields, credentials, LINE identifiers and unrestricted command payloads are excluded. Migration 012 captures immutable assignment labels for new schedules; unknown historical labels remain unknown, with any fallback current labels explicitly marked. Excel user input remains literal string cells, including formula-like text and leading-zero phones. PDF embeds bundled Thai/Latin fonts, paginates long fields and explicitly represents unsupported glyphs as Unicode code points; Excel retains the literal original text. Files are generated in memory, without a persistent report cache. Municipal field acceptance O-06 remains pending; the monthly aggregate workbook is documented above.
