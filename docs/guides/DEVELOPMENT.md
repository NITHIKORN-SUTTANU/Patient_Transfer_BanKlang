## Setup

Install the dependencies with `npm install` if needed. Follow [database setup](DATABASE.md), configure private `.env` settings and apply migrations. Configure staff accounts as described in [the API guide](API.md); synthetic seed users do not have usable passwords by default. Driver accounts require an active linked roster and availability windows.

Run the API and frontend in separate terminals from the repository root:

```powershell
npm.cmd run dev:api
```

```powershell
npm.cmd run dev
```

Open the URL printed by Vite. The development server proxies `/api` to the configured local API target.

- `/staff/login`: verified dispatcher/driver/admin login. The token stays in memory; document reload requires login again.
- `/dispatcher/*` and `/driver/*`: role-guarded API-backed flows. See the plan for outstanding functionality and verification limitations.
- `/booking/*`: existing screens with LIFF identity, recorded consent, owner-scoped profiles, intake/status/cancellation APIs. Missing LINE configuration blocks citizen login. Unsaved drafts stay in memory through navigation/errors, not document reloads; submitted records reload from the API. No browser demo records are reused.
- `/admin/*`: verified admin access, staff account and vehicle/driver management, working-window create/edit/retirement, minimized audit and aggregate-only trip history. Hospital/village/depot/closure controls use revisioned and audited APIs; location edits queue dispatcher reviews while retaining old booking/schedule snapshots. No browser demo records are reused.

LINE configuration is explained in [LINE setup](LINE-SETUP.md). Keep secrets in the private environment; do not commit or paste them into documentation. Real delivery is separately gated and is not started automatically by the API. Live messaging requires an authorized test procedure.

## Synthetic load measurement

Run `npm.cmd run test:performance` for the latency/failure-accounting checks, then `npm.cmd run test:load` with local `DATABASE_TEST_ADMIN_URL` and PostgreSQL running. The load command creates and cleans up a unique temporary database using all current migrations and synthetic master data. It never targets the development application database or sends real messages. Run it separately from browser suites, builds and other load generators. The default measurement is 60 seconds; `LOAD_DURATION_SECONDS` may select an explicit 30–300-second window. Setup and warm-up are excluded; all requests started before the measurement deadline are drained and included in elapsed time.

This is a provisional workload for O-07 review, not the agreed production workload or final SRS acceptance. Fifty distinct synthetic principals/sessions use the real loopback HTTP API: 35 citizens, ten dispatchers, four separately rostered drivers and one administrator. Sessions are inserted only by the temporary fixture after roster linking; authentication/login/LINE throughput is excluded, and public login throttles are unchanged. Each actor makes one request at a time, then waits one second. All actors start together; this closed-loop workload produces bursts and reduces its achieved request rate when responses slow. It does not represent a fixed arrival rate or bound latency under arbitrary overload.

Initial data includes 189 API-created bookings (five per citizen, ten dispatcher review subjects and four assigned trips), 12 trip events, 205 notifications, 12 synthetic villages, one hospital, six vehicles and five driver rosters. The 50 test actors are additional to four seed users. Citizens read their own list/details/profiles and submit a new request every eight steps. Dispatchers list/review, append verification records, approve their own review subject once, and repeatedly confirm a non-reserving schedule with fresh revisions. Four drivers each record Start Trip through hospital handover under real shift/ownership/version checks, then read scoped work/history. One dispatcher exports a daily workbook; the admin reads accounts/resources and exports a monthly workbook. Export actors request a workbook every eight steps. Scheduling uses the unused seed vehicle/driver; driver jobs use four independent resource pairs. All consent/intake, scheduling, milestones, audit and outbox publication use real transactional APIs. No database constraint is disabled.

The harness prints environment, pool size, workload/window, initial/final counts, peak outstanding requests, achieved request rate and per-category/per-operation results. API and generator share one Node process; PostgreSQL runs in local Docker. Host CPU/RAM metadata is not a measurement of the container's resource allocation or deployment hosting capacity. Request timing runs from fetch initiation through complete response-body consumption. HTTP/transport/timeout/invalid-result failures are counted separately, and never count as successful responses within a target. P95 uses nearest rank; both all-response and successful-response p95 are reported. Normal requests use the adopted 2,000 ms target; routing commands use 10,000 ms; exports have separate results without an invented latency target. Tests require zero functional failures and at least 95% successful responses within each applicable target, while printing diagnostics before asserting those conditions.

Routing has an injected 25 ms delay per leg and synthetic verified travel durations. Its latency does not establish live-provider NFR-P03. Outside the measured window, an injected routing outage must return 503 with identical application/ledger table fingerprints. Post-run database checks reconcile successful intake/milestone/schedule/verification/export writes, verify four exact driver event sequences, and ensure repeated schedule confirmations never create extra committed reservations. Notification delivery stays disabled; queued outbox growth is included in dataset counts.

These short local measurements do not prove a reviewed workload, production 50-user capacity, live provider latency, real-device/browser/LINE behavior, sustained load, externally hosted HTTP/TLS behavior or monthly availability. Record actual results and remaining limits in the integration plan; do not treat a fast error or a local synthetic pass as production acceptance. Protected backups and deployment-host recovery remain separate operational gates.

For opt-in diagnostics under the same workload, use PowerShell:

```powershell
$env:LOAD_DIAGNOSTICS = 'true'
try { npm.cmd run test:load } finally { Remove-Item Env:LOAD_DIAGNOSTICS }
```

The test fixture wraps API pool access and request handlers only for that run. It reports per-request pool acquisition, operational-lock wait, SQL round-trip duration, routing wall time and time outside those waits, plus event-loop utilization/delay and the slowest intake breakdowns. No SQL text/parameters, request bodies, tokens, patient names or identifying paths are retained in the report. SQL timings are client-observed and include driver/network/event-loop effects; they are not pure PostgreSQL execution timings. Parallel route intervals are merged rather than added. Component percentiles describe different requests and must not be summed. Instrumentation has overhead; compare equivalent diagnostic runs and retain ordinary workload results separately.

`test:performance` also verifies constant-query page hydration, ordering and ownership rejection, alongside failure accounting, complete-body timing and diagnostic attribution. The real staff pagination suite compares all 100 first-page records with independently authorized detail responses. The integration plan records measured changes and remaining latency limits; a batching optimization is not evidence of final production acceptance.

## Synthetic availability rehearsal

Run `npm.cmd run test:availability` with local `DATABASE_TEST_ADMIN_URL` and PostgreSQL available. It runs calendar/accounting tests, two local HTTP failure tests, six journal tests and eight real API/temporary-PostgreSQL canary scenarios (including recovery). Each database scenario creates and cleans up its own generated database; the development database/container/volumes remain intact. No real LINE/routing provider, message sender, browser, deployment or external alert is involved.

The healthy canary verifies synthetic server-side LINE exchange, authenticated citizen identity, current consent, committed intake and status, real dispatcher password login and review, approval, non-reserving schedule, committed assignment, execution-day driver login/scoped job access and committed Start Trip, then reauthenticates the citizen and reads the committed start state. It is deliberately a mutating test helper for isolated synthetic fixtures, not a production monitoring command. Never point it at a live patient service. PostgreSQL assertions verify exact committed event sequences and retained state after failures; queued messages remain PENDING with zero send attempts.

Controlled cases inject a routing-provider failure, booking-write trigger failure, driver-event trigger failure, revoked driver session, API database-access failure and identity-provider failure. These are real API responses against temporary PostgreSQL with injected external/failure boundaries, not fabricated operational responses. Only the database-access case makes `/api/health` fail; all other cases prove that green connectivity does not imply usable critical service. Separate local HTTP stubs prove that a homepage or timeout cannot count as success. A revoked canary credential is a probe authentication finding that requires triage in a real deployment; this rehearsal does not automatically declare a production-wide incident from it.

The pure `availabilityReport` function in `scripts/operations/availability.mjs` requires a reporting month, explicit calendar label and published open dates, timezone-aware observation window, and non-overlapping **system-wide** state intervals (`available`, `unavailable`, `unknown`). It applies fixed 06:00–16:00 Bangkok windows only on the supplied dates; it invents no weekday/holiday calendar. All unavailability inside those windows counts, including maintenance/provider failures. Reconcile overlapping component incidents into one system timeline before accounting; overlaps are rejected to avoid double-counting. Adjacent intervals are allowed. Output retains the exact calendar, window, coverage and minute totals.

Missing observations and explicit unknown intervals remain unknown: availability is null/incomplete rather than a false success, and monthly target acceptance is withheld. No service minutes produces `N/A`. Partial-month results are labelled and cannot establish monthly acceptance; service minutes outside the observation window are reported separately. A complete known month uses `100 * (service minutes - unavailable minutes) / service minutes`, with no rounding into a 99.5% target pass. Tests include Bangkok/hour boundaries, closed dates, exact threshold misses, leap day, December rollover and invalid/overlapping inputs.

The integration demonstration maps scenario results to explicitly invented ten-minute intervals: 80 synthetic service minutes, twenty available and 60 unavailable. Those intervals test accounting and are **not** wall-clock downtime observed during the short HTTP checks. The report remains partial-month with monthly acceptance null. Actual pilot/monthly observation, deployment-host durable collection, approved cadence/gap policy, probes and reviewed alert ownership/delivery remain pending under O-07. Record real deployment evidence separately from synthetic rehearsal results; retain the integration plan as the single progress record.

### Probe journal and bounded replay

`scripts/operations/probe-journal.mjs` adds opt-in `collectProbe`, `readProbeJournal` and `replayProbeJournal` functions. The existing availability rehearsal uses them with isolated local canaries and a temporary journal, then cleans up only its generated test directory. There is no background daemon, automatic probe schedule, live URL command or enabled external alert. A caller must supply an existing journal directory and explicit policy. The rehearsal policy is labelled `provisional-synthetic-v1`, with 60,000 ms cadence and 120,000 ms maximum sample age; these are test inputs awaiting O-07 review, not new SRS values or approved municipal monitoring settings.

Collection timestamps the start and completion itself. Actual-clock and injected-clock records are labelled `system` and `controlled`, and cannot mix within a stream. Successful results require all named critical-service checks; health alone is insufficient. Unexpected collector errors, missing/contradictory checks or malformed results become `unknown`. Records allow only generated observation identity, scope, policy, canonical UTC timestamps, state, health boolean and allowlisted failure check/code. Extra probe fields, credentials, raw errors, patient data and URLs are not copied into the journal.

Replay infers state only from a sample's completion until the earlier of the next probe's start, its maximum-age expiry or the observation end. Probe execution time, stale tails, missing samples and collector errors remain unknown. Available and unavailable samples both expire. Cadence describes the expected sampling plan; maximum age is the explicit permitted carry-forward horizon. This bounded forward inference does not establish exact incident onset/recovery times or continuous service between checks. Unknown service time withholds an availability percentage/target pass. The controlled-clock fixture proves 170 seconds available, 120 unavailable and 160 unknown in a 450-second window, including missed cadence and recovery.

Each JSONL append is flushed with file sync and guarded by an exclusive cooperating-writer lock file. The API never rewrites/truncates prior entries; exact sample replays are idempotent, while conflicting identities, overlapping/backward times, mixed clocks or policy changes are rejected. Readers validate version, allowlisted schema, sequence and SHA-256 links. A missing record within the chain, reordering or changed content fails closed. Supplying a separately trusted head `{ sequence, hash }` also detects complete-tail deletion. The chain alone cannot detect an attacker rewriting/re-hashing the entire file or deleting complete tail records without that external anchor. This is not WORM storage, signing or a production access-control guarantee.

A stale lock, incomplete/corrupt tail, read/write failure or 4 MiB size limit stops journal use; there is no automatic lock stealing, tail repair, rotation or deletion. Reconciliation, storage ACLs (including Windows), trusted anchors, protection/backup and retention remain deployment/O-04/O-07 work. Records are minimized but still require an approved operational storage procedure. A crash/power-loss-safe deployment has not been demonstrated by these local file tests.

The real API fixture now records healthy → failure → recovery with actual collector timestamps and replays those records separately from the invented ten-minute demonstration. If that real window falls outside 06:00–16:00 Bangkok service hours, it correctly reports `N/A`; it is never shifted into open hours to produce a passing percentage. Replay callers must split cross-month runs into individual reporting windows; the fixture replays the last month while validating the complete run chronology. Both outputs remain synthetic/partial observations with monthly acceptance withheld. Six journal tests cover restart/idempotency, sanitization, bounded gaps, conflicting clocks/policies/identities, corruption, trusted-anchor limits and concurrent writers.

### Local synthetic alert reconciliation

`scripts/operations/probe-alerts.mjs` evaluates the validated journal and returns sanitized local transition events plus a caller-carried checkpoint. `npm.cmd run test:availability` now includes nine alert tests and evaluates the eight real API probe scenarios through this layer. It opens one service-check episode and one credential/configuration episode, emits no duplicate transition on repeated evaluation, then recovers each once on the final complete canary. No application endpoint, UI, notification sender or background evaluator is enabled.

Inputs require the recorded sampling policy and an explicit duty policy: label `provisional-local-alerts-v1`, mode `published_hours_only` or `always_for_rehearsal`, and explicit published dates. Published hours are fixed 06:00–16:00 Bangkok. Always-on duty exists only for the synthetic rehearsal and is not an approved municipal rota. New findings are gated by their evidence time; historical findings may be recorded later. Closing time never clears existing findings. A qualifying complete recovery may resolve them outside duty hours. Owners, acknowledgement deadlines and production delivery settings remain unassigned.

Categories separate service-check failure, probe credential/response configuration, collector failure, inaccessible/untrusted journal and missing/stale observations. HTTP 401/403 and malformed probe responses are configuration findings requiring triage. Every event has `confirmedServiceOutage: false`: local findings do not automatically establish a production-wide incident or change downtime accounting. Journal/read errors are sanitized without copying paths or raw exceptions. Empty, unknown or stale results cannot imply healthy service.

Within an episode, new bad evidence updates the checkpoint without opening another alert. Opening/recovery IDs are deterministic and carry source sequence/hash, occurrence/evaluation time and the synthetic evaluator identity. Recovery requires a newer complete available record, still within maximum age at evaluation, whose probe began after the latest adverse evidence. Green health alone, restoring read access to an old journal, a stale healthy point or a formerly future-dated point cannot resolve findings. Recovery barriers never move backwards during historical backfill. Missed sampling horizons are reconciled as gaps; replay does not treat ordinary probe execution time as a new incident on every poll.

Pass the returned checkpoint on the next evaluation, including after serialization/restart. It retains the trusted journal prefix, active episode identities and policy hashes; changed policies, backward evaluation time, altered state or journal-prefix rollback fail closed. The checksum detects accidental changes, not malicious rehashing. The pure evaluator still returns local events only; use the persistence wrapper below to retain its checkpoint and transition history. External delivery and delivery acknowledgement remain unimplemented. Production use still requires protected storage, trusted anchors, ownership, incident reconciliation and an approved duty/cadence policy. These tests do not establish live alert response or monthly uptime.

### Durable local alert store

`scripts/operations/alert-store.mjs` adds explicit `initializeAlertStore`, `evaluateAndPersistAlerts`, `readAlertStore` and `recoverAlertStore` operations. Supply an absolute new directory beneath an existing parent; initialization refuses existing or partially initialized storage. The wrapper derives prior evaluator state from committed history and refuses a caller-supplied `previous` override. No store is created implicitly when a reader encounters missing storage. The rehearsal uses generated temporary directories and preserves the development application/database.

Each numbered immutable commit contains both the evaluation's transition events and full checkpoint in one checksummed, hash-linked envelope bound to the store identity. It is written to a unique staging file, synced, then atomically published by a same-directory hard link that cannot overwrite an existing generation. State/history consistency, event uniqueness, policies, chronology and probe-prefix continuity are validated before publication and on replay. An opening cannot disappear from the checkpoint without its recovery event. Readers reconstruct the active episodes and complete history from commits.

`checkpoint.json` is a derived cache, atomically replaced from a synced staging file. A missing or older cache may be rebuilt only from a fully validated committed chain. A contradictory/corrupt/ahead cache, missing published generation, corrupt commit, changed policy or unknown directory artifact stops processing; it is never silently discarded or reset. `readAlertStore` reports cache status; `recoverAlertStore` explicitly rebuilds a valid missing/stale cache. Writers also reconcile that cache before resuming. Exact repeated evaluation at the same time/state does not publish another generation or transition. Events remain available in committed history even if the caller lost the successful response; no external delivery is performed or acknowledged.

Unpublished staging is excluded from history, reported as an artifact count and never automatically promoted/deleted. An interrupted published staging file may share an inode with its immutable commit; do not edit artifacts in place. A before-publication interruption leaves the prior committed state authoritative. An after-publication interruption retains the new events/checkpoint together even if the cache is stale. Exclusive cooperating-writer locks protect initialization/read/rebuild/evaluation. A killed writer leaves its lock for explicit reconciliation; there is no automatic lock stealing. The abrupt-child-exit test removes only the known test lock after confirming that exact process has exited, then verifies replay/cache recovery without duplicate history. This is a test procedure, not an approved production recovery runbook.

The availability suite includes eleven reported persistence checks (including four injected boundary subcases), alongside the earlier cases. It injects interruptions after commit staging, after publication, before cache replacement and after replacement; tests abrupt process exit, concurrent writers, restart/idempotency, cache reconstruction, corrupt/gapped/conflicting histories, probe-prefix rollback and changed policies. The real API rehearsal now persists eight evaluations/four transitions, reopens the store after every evaluation and verifies that repeated calls add nothing. All records stay synthetic and sanitized.

The rehearsal caps files at 1 MiB, committed history at 16 MiB and generations at 10,000. Staging artifacts may consume additional space and require reconciliation. There is no automatic rotation/deletion or invented retention period. File contents are synced, but OS power-loss/directory-entry durability, deployment ACLs, encrypted/off-host protection and live monitoring are unproven. Checksums/hash chains are not signatures or WORM storage. An optional separately trusted store-head anchor detects known rollback; whole-store rollback/rehashing cannot be ruled out without independent protected anchors. Storage custody, scheduling, reviewed owners/delivery, retention and actual pilot/monthly evidence remain O-04/O-07/deployment work.
